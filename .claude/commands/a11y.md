# Accessibility (a11y) Review

Revisa el componente seleccionado para problemas de accesibilidad. El proyecto usa Radix UI (que tiene buen soporte a11y built-in) y Tailwind.

## Checklist

### Semántica HTML
- ¿Se usan elementos HTML semánticos correctos? (`button` para acciones, `a` para navegación, `nav`, `main`, `header`, etc.)
- ¿Hay `div` o `span` con `onClick` donde debería haber `button`?
- ¿Los encabezados (`h1`-`h6`) tienen jerarquía correcta?
- ¿Los formularios tienen `label` asociados a cada input?

### ARIA
- ¿Elementos interactivos sin texto visible tienen `aria-label`?
- ¿Estados dinámicos se comunican con `aria-live`, `aria-expanded`, `aria-selected`?
- ¿Los modales tienen `aria-modal="true"` y gestión de foco?
- ¿Se abusa de roles ARIA donde el HTML semántico es suficiente?

### Foco & Teclado
- ¿Todos los elementos interactivos son accesibles por teclado (Tab)?
- ¿El orden de tabulación es lógico?
- ¿Los modales y dropdowns atrapan el foco correctamente? (Radix lo hace automáticamente)
- ¿Hay `tabIndex` negativo en elementos que no deberían ser focusables?

### Visual
- ¿Los colores de texto tienen contraste suficiente (4.5:1 para texto normal, 3:1 para texto grande)?
- ¿La información no se transmite solo por color?
- ¿Los focus rings son visibles? (no `outline-none` sin reemplazo)

### Web3 específico
- ¿Los estados de carga de transacciones se anuncian a screen readers (`aria-live`)?
- ¿Las addresses de wallet están en `<code>` o similar para indicar que son datos técnicos?
- ¿Los errores de transacción son descriptivos y accesibles?

## Output
Para cada problema de a11y:
- **Severidad**: Blocker (impide uso) / Major (dificulta uso) / Minor
- **Problema** con el código actual
- **Fix** con el código corregido
- **Estándar**: referencia a WCAG si aplica
